# 14. Journey 版本管理

## 学习目标
理解 Journey 版本的目的、运行版本限制、版本切换和在途 Contact 的影响。

## 1. 为什么需要版本
Journey 版本用于保留流程定义的历史状态，使修改后的新流程与已运行流程有清晰边界。版本也便于审计、问题追踪和发布回滚决策。

## 2. 版本原则
- Draft / 未激活版本可用于设计和验证。
- 已激活版本处于运行状态时，不能把它当作普通草稿随意修改。
- 修改运行中的旅程通常通过创建新版本完成。
- 新版本发布后，已在旧版本中的 Contact 如何处理，需结合发布选项和产品行为明确确认。

## 3. 版本切换前评估
| 影响对象 | 需要确认 |
|---|---|
| 新进入 Contact | 新版本何时接收入口 |
| 旧版本在途 Contact | 继续旧版本、迁移或其他处理方式 |
| Wait 中 Contact | 是否按原 Wait 继续 |
| 已触发消息 | 已排队或已发送消息无法简单撤回 |
| Entry Event | 新版本入口定义是否兼容 |
| 数据字段 | 新旧版本所需字段是否同时存在 |

## 4. 版本命名建议
使用业务名 + 版本号 + 变更日期，例如 `WelcomeJourney_v2_202611`。不要在名称中写入客户个人信息或敏感数据。

## 5. 操作流程
1. 记录变更原因、影响范围和回退方案。
2. 创建新版本。
3. 修改入口、Activity 或条件。
4. Validate 并使用测试 Contact 测试。
5. 明确旧版本在途 Contact 的处理策略。
6. 在批准窗口 Activate 新版本。
7. 监控新旧版本入口和 Activity 数量。

## 常见问题
- 新版本激活后旧 Contact 路径不一致：检查版本切换选项和旧版本在途处理。
- 新字段不可用：检查新版本入口字段、DE 结构和数据模型。
- 回退困难：发布前应保存配置、测试证据和变更记录。

## Checklist
- [ ] 变更内容和原因已记录
- [ ] 新版本已 Validate / Test
- [ ] 在途 Contact 策略已确认
- [ ] 入口字段兼容性已检查
- [ ] 回退方案和监控指标已准备
