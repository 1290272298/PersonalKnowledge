# 02. Journey

## 学习目标
理解 Journey 的生命周期、Contact 执行模型、版本和运行状态。

## 1. Journey 的组成
Journey 是一套已配置的客户旅程定义，通常包含一个入口事件，以及一系列 Activity、路径、目标和退出规则。一个 Journey 版本只有一个 Entry Event；旅程结束通过没有后续节点的路径或退出行为实现。

## 2. 生命周期
```
Create / Draft → Configure → Validate → Test → Activate
                                           ↓
                                      Running
                                           ↓
                                  Stop / Complete
```
具体状态名称和可执行操作以当前 UI 为准。Validate 主要检查配置完整性，不等于业务逻辑已被充分测试。

## 3. Contact 的执行模型
Contact 进入 Journey 后，系统根据 Contact Key 识别其身份，并为其维护旅程执行状态。不同 Contact 可以位于不同 Activity。入口数据和后续活动输出可作为 Journey Data 使用；需要读取关联客户属性时，可能需要 Contact Data 和正确的数据模型关系。

## 4. Journey Data 与 Contact Data
| 类型 | 含义 | 适用场景 |
|---|---|---|
| Journey Data | 进入旅程时携带的数据、活动输出 | 判断本次事件的订单号、注册来源 |
| Contact Data | Contact Builder 中与 Contact 关联的数据 | 当前会员等级、客户主档属性 |

如果入口记录之后被更新，Journey Data 通常代表进入时的上下文，不应假定它会自动变成最新主档值。需要实时或较新的客户属性时，确认使用 Contact Data，并检查 Attribute Group 关系和数据更新时间。

## 5. Contact Key
Contact Key 是跨渠道关联 Contact 的稳定标识。Email Studio 中 Subscriber Key 通常映射到 Contact Key 的业务标识。不要把可变的 Email Address 作为默认主键，也不要在不同渠道使用不一致的 Key。

## 6. 设计与操作
1. 为 Journey 定义唯一且可识别的名称。
2. 先确定入口事件、数据字段和 Contact Key。
3. 画出正常路径、异常路径、重复进入和退出路径。
4. 为每个分支写明条件及数据来源。
5. 测试不同类型 Contact 的路径。

## 常见问题
- **Contact 进入后字段值为什么与 DE 当前值不同？** 检查 Journey Data 与 Contact Data 的选择，以及数据写入时点。
- **同一个人出现多个 Contact？** 排查不同来源的 Contact Key 是否一致。
- **旅程运行中能否直接修改？** 通常需要创建新版本；发布前评估在途 Contact 的迁移策略。

## Checklist
- [ ] Journey 名称、用途和所有者明确
- [ ] Entry Event 与 Contact Key 明确
- [ ] Journey Data / Contact Data 使用场景明确
- [ ] 版本切换和在途 Contact 处理方案明确
