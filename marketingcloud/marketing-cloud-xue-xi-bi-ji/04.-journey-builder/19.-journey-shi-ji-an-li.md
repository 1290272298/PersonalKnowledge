# 19. Journey 实际案例

## 案例：新客户注册与购买培育

### 1. 业务需求
客户注册后发送欢迎邮件；等待一段时间后根据互动行为发送不同内容；若客户已购买，则不再发送购买提醒。

### 2. 数据设计
| 字段 | 示例 | 说明 |
|---|---|---|
| ContactKey | C00001 | 稳定 Contact Key |
| EventId | REG-2026-0001 | 注册事件唯一标识 |
| EventDate | 2026-11-01T09:00:00+09:00 | 业务发生时间 |
| EmailAddress | test@example.invalid | 测试邮箱 |
| Locale | ja-JP | 内容语言 |

订单状态通过与 Contact Key 关联的数据模型提供，需确认更新时点。

### 3. Journey 流程
```
Registration Event
       ↓
Welcome Email
       ↓
Wait 2 Days
       ↓
Engagement Split (Clicked?)
   ┌───┴────┐
  Yes      No
   ↓        ↓
Guide     Reminder
 Email      Email
   └───┬────┘
       ↓
Purchase Goal / Exit Criteria
       ↓
      Exit
```

### 4. 设计重点
- Contact Key：入口、Email Studio、Contact Builder 使用一致的标识。
- Event ID：同一注册事件重试时可追踪，不误当作新注册。
- Engagement：等待足够时间，且不要把 Open 等同真实阅读。
- Purchase：通过订单数据更新 Contact Data；评估同步延迟和退出时点。
- Re-entry：一次性欢迎流程通常限制重复进入；若业务允许再次注册，必须定义新事件规则。
- Email：确认 Send Classification、Sender Profile、Delivery Profile、订阅状态和动态字段。

### 5. 测试案例
| 测试 Contact | 输入情况 | 预期 |
|---|---|---|
| T01 | 正常注册，点击邮件 | Guide 路径 |
| T02 | 正常注册，未点击 | Reminder 路径 |
| T03 | 注册前已购买 | 按业务规则跳过/退出 |
| T04 | 重复发送相同 Event ID | 不产生非预期重复旅程 |
| T05 | Contact Key 为空 | 拒绝或进入异常处理，不直接上线 |
| T06 | 购买状态延迟更新 | 验证是否可能误发购买提醒 |

### 6. 发布和监控
先在测试环境验证入口、分支、购买退出和发送资格；发布后监控 Entry、Activity、Send、Bounce、Click、Goal。出现异常先定位 Contact 与节点，不立即重复触发入口事件。

## Checklist
- [ ] 入口字段与 Event ID 已定义
- [ ] Contact Key 一致
- [ ] 分支和 Remainder 路径完整
- [ ] 购买数据关系和延迟已测试
- [ ] 重复进入和退出行为已测试
- [ ] 发送资格和 Tracking 已验证
