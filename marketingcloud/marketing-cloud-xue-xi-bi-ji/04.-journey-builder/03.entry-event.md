# 04. Entry Event

## 学习目标
理解事件触发、事件定义、API Event 与数据事件的区别，并设计可重试、可追踪的事件接入。

## 1. Entry Event 是什么
Entry Event 是触发 Contact 进入 Journey 的具体事件定义。Entry Source 说明事件/数据从哪里来，Entry Event 则定义旅程如何识别该次进入。Journey Specification 中由 trigger 关联事件定义；一个 Journey 版本只能有一个 Entry Event。

## 2. 事件流程
```
业务系统产生事件
      ↓
校验 Contact Key / Event Key
      ↓
发送事件或写入入口数据
      ↓
Journey 接收并评估
      ↓
Contact 进入旅程
```

## 3. API Event
API Event 适合外部应用在注册、下单、申请等业务动作发生时实时触发 Journey。设计时应确认：
- Installed Package / API Integration 配置与授权
- Event Definition Key、请求结构和必需字段
- Contact Key 与事件字段值
- 失败重试、超时、重复请求的处理
- API 返回成功与 Contact 实际进入之间的监控链路

**幂等设计**：建议业务系统为每个业务事件生成唯一 Event ID，并在调用端记录请求结果。重试时使用同一业务事件标识，避免把一次业务动作误当成多次新事件。具体去重行为需以所用入口机制为准，不能只依赖 Journey Re-entry 设置。

## 4. Salesforce Data Event
通过 Marketing Cloud Connect 等已配置集成使用 Salesforce 数据事件时，应检查 Salesforce 对象、触发条件、字段权限、Connector 用户和同步状态。可用对象与事件能力取决于组织配置和产品许可。

## 5. 事件数据设计
建议至少记录：
- ContactKey：稳定的客户标识
- EventId：业务事件唯一标识
- EventDate：业务发生时间（含时区约定）
- EventType：事件类型
- 业务属性：后续个性化或分支需要的字段

## 6. 常见问题
**API 返回成功但客户未进入？** 检查 Event Definition Key、Contact Key、事件字段格式、Journey 是否已激活、入口版本和执行历史。

**同一事件多次进入？** 检查发送端重试策略、Event ID、重复写入和 Journey Re-entry。

**事件晚到？** 明确迟到事件是否仍可进入、是否需要按 EventDate 排序，以及是否会影响已过期的营销内容。

## Checklist
- [ ] Event Definition 与 Journey 版本对应
- [ ] Contact Key 格式统一
- [ ] Event ID 唯一且可追踪
- [ ] 请求超时和重试策略明确
- [ ] 事件时间、时区和迟到规则明确
- [ ] 入口失败有监控和补偿机制
