# 11. Exit Criteria

## 学习目标
理解 Exit Criteria 的用途、评估时点及其与 Goal 的区别。

## 1. 功能
Exit Criteria 定义哪些 Contact 不再适合继续 Journey，满足条件时从旅程中移除。典型场景：客户已购买，不应再收到购买提醒。

## 2. 条件设计
可使用支持的 Contact 属性/过滤条件构建退出规则。设计时必须确认数据来源、更新频率、关系路径和字段空值。若购买状态由外部系统更新，需评估数据同步延迟与评估周期。

## 3. Exit Criteria 与 Goal
| 项目 | Exit Criteria | Goal |
|---|---|---|
| 目的 | 移除不应继续旅程的 Contact | 衡量希望促成的业务行为 |
| 统计意义 | 重点是退出控制 | 用于目标达成统计 |
| 是否必需 | 依旅程需求 | 可选 |
| 可否触发退出 | 是 | 可按 Exit Option 配置 |

Goal 可以兼作退出条件，但二者不是同一概念。Goal 达成统计用于衡量成效；Exit Criteria 关注是否继续旅程。

## 4. 评估时点
退出规则并不代表字段一变化就必然瞬间退出。需结合 Journey 的评估机制、Wait Activity 和数据更新时间验证。对“购买后不得再发送”这类强约束，应在发送前设计可靠的资格校验/抑制机制，不要只依赖较长间隔后的退出评估。

## 5. 操作步骤
1. 定义明确的退出业务事件。
2. 确认数据源与字段更新时点。
3. 配置 Exit Criteria。
4. 测试条件满足前后 Contact 的旅程状态。
5. 验证退出后是否仍有已排队/已触发的发送。

## 常见问题
- 已购买仍收到邮件：检查退出条件是否使用正确数据源、同步延迟、评估时点和发送是否已触发。
- 不该退出却退出：检查空值、字段类型、条件组合和关系路径。
- 退出后再次进入：检查 Re-entry 设置和新的入口事件。

## Checklist
- [ ] 退出条件与业务规则一致
- [ ] 数据源和更新时间明确
- [ ] 评估时点经过测试
- [ ] 已触发发送与退出后的行为已评估
- [ ] Re-entry 规则明确
