# 01. Personalization 介绍

## 学习目标
了解 Marketing Cloud Personalization 的定位、核心能力，以及它与 Marketing Cloud Engagement 的区别。

## 1. 产品定位
Marketing Cloud Personalization 用于实时采集用户行为、构建用户与商品/内容数据、进行受众判断和个性化体验决策。典型场景包括网站推荐、个性化 Banner、内容推荐、活动触达和行为分析。

## 2. 与 Marketing Cloud Engagement 的区别
| 产品 | 主要职责 | 典型能力 |
|---|---|---|
| Marketing Cloud Engagement | 多渠道营销沟通与自动化 | Email、Journey、Automation、Mobile |
| Marketing Cloud Personalization | 实时行为数据与个性化体验 | Sitemap、Catalog、Web Template、Campaign |

两者可以通过数据导入、API 或产品集成协作，但数据模型、权限和运行方式并不相同。不要将 Personalization 的 User Profile 与 Engagement 的 Contact / Subscriber 直接视为同一对象。

## 3. 核心组件
- Sitemap：网站端 JavaScript 配置，采集页面、用户行为和业务事件。
- User Profile：匿名或已知用户的属性与行为上下文。
- Catalog：商品、内容、类别等可推荐实体。
- Campaign：定义受众、策略、内容和投放时机。
- Web Template：定义个性化内容的呈现逻辑。
- Content Zone：网站中允许展示个性化内容的位置。

## 4. 典型数据流程
```
Visitor → Sitemap → Events / Identity
                     ↓
              User Profile + Catalog
                     ↓
               Segmentation
                     ↓
              Campaign / Template
                     ↓
                Website UI
```

## 5. 适用场景
- 浏览商品后推荐相关商品。
- 根据访客兴趣显示不同 Banner。
- 对已登录用户提供个性化内容。
- 根据购物车、浏览和购买事件进行实时受众判断。

## 6. 实施前提
确认 Personalization 账号、数据集、站点域名、SDK/Sitemap 配置、用户权限和隐私同意机制。不同环境（开发、测试、生产）应使用明确的数据集和部署配置。

## 常见问题
**Personalization 是否等同于 Journey Builder？** 不是。前者偏实时数据和体验个性化，后者偏 Contact 旅程编排。

**登录前后的访客一定会合并吗？** 取决于身份识别和 Alias/Identity 配置；必须验证身份关联规则，不应假设自动合并。

- [ ] 数据集和环境明确
- [ ] 身份规则及隐私同意已设计
