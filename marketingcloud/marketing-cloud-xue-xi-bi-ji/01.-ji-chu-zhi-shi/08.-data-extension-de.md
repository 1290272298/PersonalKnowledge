# 08. Data Extension（DE）

## 1. 学习目标

掌握 DE 的数据结构、字段类型、主键、Send Relationship、Sendable / Non-Sendable、更新方式和数据保留；能够设计一张可安全用于发送或数据处理的 DE。

## 2. Data Extension 是什么

Data Extension 是 Marketing Cloud Engagement 中用于保存结构化数据的表。它可以保存客户资料、交易、受众、Journey 入口、产品目录、导入结果和处理结果。

DE 是数据容器，不等于 Subscriber 或 Contact。DE 中有一列 SubscriberKey / ContactKey，也不意味着记录自动成为 Subscriber 或 Contact。

## 3. DE 的主要属性

| 属性 | 作用 | 设计注意 |
|---|---|---|
| Name | UI 中显示的名称 | 按业务用途命名 |
| Customer Key / External Key | API 和集成中识别 DE 的稳定键 | 建立命名规范，避免随意变更 |
| Fields | 定义数据结构 | 数据类型、长度、是否可空 |
| Primary Key | 唯一标识一条记录 | 组合主键可用于多字段唯一性 |
| Sendable | 是否用于发送场景 | 需要设置 Send Relationship |
| Send Relationship | 将 DE 字段映射到 Subscriber Key 等发送身份 | 确保映射值稳定且正确 |
| Retention | 数据保留和删除规则 | 建 DE 前明确生命周期 |

## 4. 字段类型与数据质量

常见类型包括 Text、Number、Decimal、Date、Boolean、EmailAddress 等，具体类型和长度限制以当前 UI 文档为准。

设计原则：
- Email Address 字段使用正确的 EmailAddress 类型（发送 DE 中通常应有明确的 Email 地址字段）。
- Contact Key / Subscriber Key 使用 Text。
- 金额、比率等字段选择合适数值精度。
- 日期时间统一时区约定，避免把 JST 当成 UTC。
- 对空值、默认值、非法字符和字段长度定义处理方式。
- 不要把数值 ID 与字符串 ID 混用，避免 JOIN 和关系匹配失败。

## 5. Primary Key 与业务唯一性

Primary Key 用于防止同一 DE 中出现重复键值。它不一定等于 Contact Key。

例子：
- 客户主数据：CustomerID。
- 订单明细：OrderID + LineNumber。
- 客户每日行为：CustomerID + EventDate + EventType。
- 产品目录：SKU。

设计前要确认业务唯一性。如果一个客户一天可有多条行为记录，就不能只用 CustomerID 作为主键。

## 6. Sendable 与 Non-Sendable

### Sendable DE
可用于支持的发送场景，需要配置 Send Relationship，将 DE 中某字段映射到 Subscriber Key / Contact Key（依 UI 选项和场景而定），并提供发送所需 Email Address 等字段。

### Non-Sendable DE
用于参考、交易、事件、目录、日志或中间处理数据，不直接作为发送目标。

Sendable 不代表所有记录都能发送。还要检查 Subscriber Status、Send Classification、Suppression、Consent、List Detective、发送配置和地址质量。

## 7. DE 与 Contact Model

若要在 Contact Builder / Journey 中使用 Contact Data，需要在 Data Designer 中建立正确 Attribute Group 和关系。DE 字段名相同不等于自动关联；关联字段应在类型和值上匹配，通常优先使用 Contact Key。

## 8. 数据更新模式

| 模式 | 典型行为 | 风险 |
|---|---|---|
| Overwrite | 用本次结果替换目标数据集内容 | 可能清空旧记录 |
| Append | 在目标中追加记录 | 重复数据、主键冲突 |
| Update | 按主键更新已存在记录（具体行为看 Activity） | 未命中记录通常不会自动新增 |
| Add and Update / Upsert | 按配置新增或更新 | 字段映射与主键必须正确 |

不同导入工具、API、SQL Activity 的具体行为可能不完全相同，必须按所用 Activity 的定义验证。特别区分“文件中没有某字段”和“文件中该字段为空值”。

## 9. 数据保留与删除

DE 可配置 Row-Based / Object-Based Retention 等策略。数据超过保留条件后可能被永久删除；删除处理时间并不一定等于到期的精确时刻。

设计时要回答：
- 业务和法规要求保留多久？
- 是否需要保留历史快照？
- 是否需要在删除前导出？
- Contact Delete 是否影响相关 Sendable DE？
- 自动化是否依赖已删除的数据？
- 谁批准保留策略变更？

不要把“用户创建的 DE 默认永久保存”当成安全策略；应主动定义生命周期。

## 10. 常见问题

### DE 有 Email 字段，为什么不能发送？
检查是否为 Sendable、Send Relationship 是否正确、EmailAddress 字段数量与类型、目标 Subscriber 是否有效，以及发送配置。

### SQL 更新后记录数变少？
检查 Overwrite、WHERE 条件、JOIN、NULL、主键和数据源刷新时间。

### 同名 DE 为什么数据不同？
检查当前 BU、Customer Key / External Key 和资源归属。

### DE 中 Status = Active，为什么还是不能发送？
DE Status 是业务字段，不等于 All Subscribers 的 Subscriber Status。

## 11. 设计 Checklist

- [ ] DE 名称、External Key 和所属 BU 已明确。
- [ ] 字段类型、长度、可空性已定义。
- [ ] Primary Key 符合真实业务唯一性。
- [ ] Sendable / Non-Sendable 选择正确。
- [ ] Send Relationship 与 Contact / Subscriber Key 对齐。
- [ ] 数据更新模式和空字段语义已测试。
- [ ] Retention、删除和备份方案明确。
- [ ] 数据量、索引/主键和 SQL 性能已评估。
