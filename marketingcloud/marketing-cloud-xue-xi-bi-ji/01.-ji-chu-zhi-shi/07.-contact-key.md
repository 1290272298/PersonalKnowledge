# 07. Contact Key

## 1. 学习目标

理解 Contact Key 是 Engagement 中识别 Contact 的业务标识；掌握它与 Subscriber Key、Contact ID、Email Address 的区别，并能设计跨渠道身份键。

## 2. Contact Key 是什么

Contact Key 是 Marketing Cloud Engagement 用于识别一个 Contact 的唯一业务值。它用于把同一个人的不同渠道地址和相关属性关联到一个 Contact 身份。

例如：

```
Contact Key = CRM-000123
  ├─ Email Subscriber Key = CRM-000123
  ├─ Mobile Address
  ├─ Push Device
  └─ Customer Attributes
```

Contact Key 应该代表“这个客户是谁”，而不是“客户当前使用哪个联系方式”。

## 3. Contact Key 与 Subscriber Key

Salesforce Contact Builder 最佳实践明确建议使用单一 Contact Key，并使其与 Email Studio 的 Subscriber Key 相同。这样可以把 Email、Mobile 等渠道信息关联到同一个 Contact。

如果项目因历史系统或多品牌业务而使用不同 Key，需要建立明确、可维护的身份映射；不能假设平台会自动理解两个不同值属于同一个人。

## 4. Contact Key 与 Contact ID

- Contact Key：由业务或集成设计提供的身份值。
- Contact ID：Engagement 内部生成的系统标识。

Contact ID / Subscriber ID 主要是内部系统代理键，不应替代 Contact Key 作为跨系统业务标识。

## 5. 设计原则

- 使用稳定且唯一的值，例如 CRM Customer ID 或 GUID。
- 使用 Text 字段；数值型 ID 导入前转换成字符串。
- 不要使用 Email Address 作为关系键，除非没有其他选择且已评估变更风险。
- 在 Enterprise 内统一命名、格式和唯一性范围。
- 同一客户的 Email、SMS、Push 数据尽可能关联到同一个 Contact Key。
- 定义匿名用户、登录识别、客户合并、删除和重新注册的生命周期规则。

## 6. 关系设计示例

```
DE_Customer
  CustomerKey (Primary Key)
  Email
  Locale
       |
       | CustomerKey = Contact Key
       v
Contact Model
       |
       +--- DE_Mobile
       |      CustomerKey
       |      MobileNumber
       |
       +--- DE_Purchase
              CustomerKey
              OrderID
              PurchaseDate
```

关联字段必须在数据类型、长度和实际值上匹配。仅仅字段名称相同并不能建立有效关系。

## 7. Key 不一致会造成什么问题

- Journey Entry Contact 与 Contact Data 无法正确关联。
- 同一个客户可能被创建成多个 Contact。
- 跨渠道行为分散，难以形成完整客户视图。
- Decision Split 读取不到预期属性。
- 退订和渠道地址可能无法按预期关联。

## 8. Key 变更注意事项

Contact Key 是核心身份标识。修改可能影响 Contact 记录、关联数据、Journey、渠道地址、历史 Tracking 和删除流程。应先在测试环境验证平台行为和迁移路径，再制定生产变更与回退方案。

## 9. 常见误区

- **Contact Key = Email Address。** 不推荐；Email 可变。
- **Contact Key = Contact ID。** 两者用途不同。
- **Subscriber Key 与 Contact Key 可以随意不同。** 可以有特殊设计，但跨渠道统一身份通常更简单可靠。
- **只要 DE 中有 CustomerID 就自动关联 Contact。** 需要 Contact Model / Data Designer 中正确的关系。

## 10. 本页 Checklist

- [ ] Contact Key 的来源和唯一范围明确。
- [ ] 字段使用 Text，数据格式一致。
- [ ] Contact Key 与 Subscriber Key 的映射明确。
- [ ] 各渠道数据使用统一身份值。
- [ ] 身份合并、匿名转登录和 Key 变更已设计。
