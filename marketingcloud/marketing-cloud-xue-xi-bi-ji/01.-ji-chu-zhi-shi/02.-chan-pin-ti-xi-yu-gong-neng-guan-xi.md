# 02. 产品体系与功能关系

## 1. 学习目标

理解 Engagement 内各组件的职责边界、数据流和依赖关系；能够根据业务需求判断使用 Email Studio、Automation Studio 或 Journey Builder，而不是把所有任务都放入同一个工具。

## 2. 以职责理解整体架构

```
数据进入 / 生成
  ├─ Import / FTP
  ├─ API / Marketing Cloud Connect
  └─ Data Extension / Contact Data
          ↓
数据建模与受众准备
  ├─ Contact Builder / Data Designer
  ├─ SQL Query / Filter
  └─ Consent / Suppression 检查
          ↓
内容与消息配置
  ├─ Content Builder
  ├─ Email Studio
  └─ Mobile 相关渠道（按许可启用）
          ↓
执行编排
  ├─ Automation Studio：任务、批处理、定时
  └─ Journey Builder：按 Contact 状态与事件推进
          ↓
反馈与治理
  ├─ Tracking / Data Views
  ├─ 报表与业务转化
  └─ 权限、审计、保留与删除
```

这不是强制的唯一执行顺序。简单的一次性发送可以不需要 Journey；某些 Journey 的入口也可以由 API Event 或其他事件触发，不一定来自 Automation。

## 3. 核心组件职责

| 组件 | 主要职责 | 输入 | 典型输出 |
|---|---|---|---|
| Contact Builder | Contact 与数据关系模型 | DE、Contact Key、Attribute Group | 可供 Contact Data 使用的数据关系 |
| Data Extension | 结构化数据存储 | Import、API、SQL、Journey | 业务/受众/事件/结果数据 |
| Content Builder | 内容资产管理 | 模板、区块、图片、文案 | 可复用消息内容 |
| Email Studio | 邮件与 Subscriber 相关管理、发送和 Tracking | Email、发送对象、分类、Profile | Send Job、发送结果 |
| Automation Studio | 按计划或触发条件运行 Activity | 文件、DE、SQL、脚本、发送任务 | 自动化处理结果 |
| Journey Builder | Contact 级客户旅程编排 | Entry Source / Event | Contact 的活动路径和消息触达 |
| Mobile Studio / Mobile 相关能力 | 移动消息渠道能力 | Mobile 联系方式、订阅与消息配置 | SMS / Push 等渠道触达 |
| Tracking / Data Views | 发送和互动数据查询 | Send / Engagement events | 发送、打开、点击、Bounce 等数据 |

具体名称、可用活动和菜单位置可能随账号启用功能与版本变化。

## 4. 数据层：DE 与 Contact Model 不等价

DE 是表结构和记录集合；Contact Builder 的 Data Designer 用于定义 DE 与 Contact 身份之间的关系。一个 DE 即使存在，也不会因为保存了 CustomerID 就自动成为 Contact Data。

设计前确认：
- DE 的主键是否真正唯一。
- Contact Key 字段的数据类型、长度和内容是否一致。
- Attribute Group 是否已建立关系。
- 一对多关系是否会产生多条匹配记录。
- Journey 中使用的是 Entry / Journey Data 还是 Contact Data。

## 5. 执行层：Automation 与 Journey 的选择

| 需求 | 优先考虑 | 原因 |
|---|---|---|
| 每天凌晨导入文件并整理 DE | Automation Studio | 批处理、定时和 Activity 链 |
| 每月计算目标客户并生成发送名单 | Automation Studio + SQL | 以数据集处理为主 |
| 注册后立即发欢迎邮件 | Journey Builder 或事件触发发送 | 以单个 Contact 的事件驱动为主 |
| 发信后等待并按互动分支 | Journey Builder | Contact 在旅程中推进 |
| 先处理数据，再让客户进入 Journey | Automation + Journey | 两者职责组合 |

不要将 Journey 理解成 Automation 的可视化版本。Automation 以 Activity 执行链为中心；Journey 以 Contact 的进入、状态和路径为中心。

## 6. 内容层：Content Builder 与 Email Studio

Content Builder 管理可复用的内容资产；Email Studio 处理邮件发送、订阅者和发送相关设置。实际工作流会根据当前 UI 和内容类型略有差异。动态内容依赖正确的数据字段和关系；字段为空时必须考虑默认内容。

## 7. 跨组件数据流示例

目标：每周向近期浏览 SUV 且具有有效营销许可的客户发送推荐。

1. 外部系统将 Customer、Browsing Event、Consent 数据导入 DE。
2. Automation Studio 校验文件和字段，使用 SQL 形成目标 DE。
3. SQL 以稳定 CustomerID 关联数据，避免一对多 JOIN 导致人数放大。
4. 目标 DE 与 Journey Entry Source 对齐 Contact Key。
5. Journey Builder 处理进入条件、等待和后续消息。
6. Email Activity 使用已配置的 Email、Send Classification、Sender Profile 等发送上下文。
7. Tracking / Data Views 供对账和效果分析。

## 8. 常见架构错误

- 把 Contact Key、Subscriber Key、DE Primary Key 当成同一个概念。它们可以使用同一个值，但职责不同。
- 把 DE 中的业务字段 Status 当成 All Subscribers 的 Subscriber Status。
- 认为所有 BU 都可以直接访问同一 DE；需要检查共享资源和权限。
- 认为 Journey Data 与 Contact Data 完全相同；两者的来源和可用范围不同。
- 认为发送完成就代表送达 Inbox；发送状态、Bounce、Spam Placement 是不同层次。
- 忽略 Tracking 数据保留期限，导致无法长期追溯。

## 9. 组件选择 Checklist

- [ ] 业务是数据批处理，还是 Contact 事件旅程？
- [ ] 数据来源、主键和更新频率明确？
- [ ] Contact Key 与 Subscriber Key 设计一致？
- [ ] 发送资格、Consent、Suppression 已定义？
- [ ] 内容所需字段可被正确读取？
- [ ] 发送上下文和 BU 明确？
- [ ] 监控、对账、重试和保留方案明确？
