# 03. Business Unit（BU）

## 1. 学习目标

理解 BU 是 Enterprise Account 内的业务组织与访问上下文；掌握资源归属、用户访问、共享资源和 Subscriber 管理之间的区别。

## 2. BU 是什么

Business Unit（BU）是 Marketing Cloud Engagement Enterprise / Enterprise 2.0 账号中的组织单位。企业可按国家、品牌、部门或业务线划分 BU，以管理用户访问、内容、数据和营销操作。

BU 不等于独立租户，也不只是文件夹。BU 的层级、可见资源和管理能力受账号结构、共享配置和权限控制。

## 3. BU 与 MID

每个 BU 有对应的 MID（Member ID / Account ID 上下文）。MID 在 API 集成、资源归属和排查中非常重要。

实际确认时应区分：
- Enterprise / Parent Account 的 MID。
- 当前登录并操作的 BU MID。
- API Token 所属的账号上下文及请求中指定的 account_id（适用时）。
- DE、Journey、Automation、Content 所属的 BU。

不要将 MID、用户 ID、Subscriber Key 或 Contact Key 混为一谈。

## 4. 为什么需要多个 BU

常见组织方式：

```
Enterprise
  ├─ Japan BU
  ├─ China BU
  ├─ Brand A BU
  └─ B2B BU
```

划分 BU 可以帮助：
- 限制用户只访问负责的业务空间。
- 分开管理品牌内容和发送活动。
- 将本地化业务与共享平台能力分开。
- 降低误选其他品牌受众或内容的风险。

但 BU 本身不是完整的数据治理方案。敏感数据访问还要通过字段设计、权限、共享方式、Consent 和操作流程管理。

## 5. BU 与资源归属

| 资源 | 设计时要确认 |
|---|---|
| Data Extension | 创建在哪个 BU？是否为 Shared DE？共享路径和权限如何？ |
| Email / Content | 是本地资产还是 Shared Content？修改共享资产会影响谁？ |
| Journey | 属于哪个 BU？入口 DE / Event 在哪个上下文？ |
| Automation | 在哪个 BU 运行？Activity 引用的 DE 和文件位置是什么？ |
| 用户 | 被分配到哪些 BU？角色和单项权限是什么？ |
| API | Token 的 MID / account context 与目标资源是否匹配？ |

不要假设“同名 DE”就是同一份数据；不同 BU 可以存在同名但不同 External Key / 记录内容的资源。

## 6. BU 与用户权限

用户可访问的 BU 范围和具体操作权限是两个维度：
- Business Unit Access：用户可以进入哪些 BU。
- Roles / Permissions：在该 BU 中可以查看、创建、更新、发送或管理什么。

Salesforce 文档说明，角色权限冲突时，显式 Deny 会覆盖 Allow；不要为了排查问题而一次性赋予所有角色。建议采用最小权限原则，按工作职责分配角色与权限。

## 7. BU 与 Subscriber / Contact

BU 资源隔离不等于 Subscriber / Contact 身份完全按 BU 隔离。Enterprise 环境中的 All Subscribers 和 Contact 管理需要结合企业层级、Subscriber Key、Contact Key、发送上下文和退订范围判断。

排查 BU 间状态联动时：
1. 确认两个 BU 是否属于同一个 Enterprise。
2. 确认 Subscriber Key / Contact Key 是否相同。
3. 确认变化发生在 All Subscribers、Publication List 还是 DE 业务字段。
4. 确认是 Global / Master Unsubscribe 还是 List-level unsubscribe。
5. 确认发送来自哪个 BU、使用哪种 Send Classification。
6. 再判断影响范围，不要只凭“在不同 BU”推断状态一定独立或一定联动。

## 8. Shared Resources

部分资源可通过共享文件夹或共享数据机制供其他 BU 使用。共享的具体能力取决于资源类型和账号配置。

共享设计应明确：
- 资源所有者和维护者。
- 哪些 BU 可读、可更新或可使用。
- 变更是否会立即影响使用方。
- 命名规范和版本管理。
- 数据更新失败时由谁负责。

## 9. BU 设计原则

- 按长期组织边界划分，不要为每个 Campaign 随意新建 BU。
- 业务隔离、数据隔离和用户权限分别设计。
- 跨 BU 数据优先定义明确的共享接口或复制流程。
- 为 API 集成明确 MID 与目标 BU。
- 对共享内容和共享 DE 建立变更管理。
- 记录 BU 层级、用途、负责人和资源清单。

## 10. 排查顺序

```
确认用户
  ↓
确认当前 BU / MID
  ↓
确认目标资源所属 BU
  ↓
检查共享设置与资源权限
  ↓
检查 Subscriber / Contact Key
  ↓
检查发送上下文 / API account context
  ↓
保存证据并验证
```

## 11. 常见误区

- **BU 就是独立数据库。** 不准确；资源归属、共享、Subscriber 和 Contact 管理需要分别判断。
- **Parent BU 自动拥有所有 Child BU 资源的完全访问权。** 不应如此假设，必须看配置和权限。
- **一个用户能登录就能操作所有资源。** 还需检查 BU Access 和具体权限。
- **相同 Subscriber Key 在不同 BU 一定是不同订阅者。** 需结合 Enterprise / All Subscribers 和发送上下文判断。
- **Shared DE 等于复制一份 DE。** 共享资源与数据复制是不同机制。

## 12. 本页 Checklist

- [ ] Enterprise 和 BU 层级明确。
- [ ] 每个 BU 的 MID、用途和负责人有记录。
- [ ] 关键资源的所属 BU 与共享方式明确。
- [ ] 用户 BU Access 和 Role / Permission 分别检查。
- [ ] API 请求的账号上下文已验证。
- [ ] Subscriber 状态范围没有按 BU 名称臆断。
