# 06. Subscriber Key

## 1. 学习目标

理解 Subscriber Key 的唯一识别作用、与 Email Address / Subscriber ID / Contact Key 的区别，并掌握设计、导入、发送和变更时的风险。

## 2. Subscriber Key 是什么

Subscriber Key 是 Marketing Cloud Engagement 中用于唯一识别 Subscriber 的文本值。它是业务选择的标识，不是系统自动从 Email Address 推导出的字段。

Subscriber Key 会影响：
- 导入或创建 Subscriber 时，系统判断是否为已有记录。
- 发送名单中重复记录的识别。
- Profile / Subscription Center 等订阅者资料更新。
- 退订事件关联到哪个 Subscriber。
- API、Tracking 和跨系统身份匹配。

## 3. Subscriber Key 与 Email Address

| Subscriber Key | Email Address | 说明 |
|---|---|---|
| CRM-000123 | a@example.com | 稳定业务 ID |
| CRM-000456 | a@example.com | 同一邮箱可对应另一个 Subscriber |
| CRM-000123 | new@example.com | Email 改变，Subscriber Key 可保持不变 |

Salesforce 建议避免使用 Email Address 作为 Subscriber Key。Email 可能变化、重复或被家庭成员共用；Key 应来自稳定的业务系统标识。

Subscriber Key 是文本字段，官方文档说明最大长度为 254 个英文字符。实际设计应统一大小写、前后空格、编码和格式。

## 4. Subscriber Key 与 Contact Key

在 Contact Builder 的最佳实践中，Contact Key 与 Email Studio 的 Subscriber Key 使用同一个值，以便跨渠道关联一个 Contact。两者概念用途不同，但推荐保持统一。

若现有项目使用不同值，应先明确映射关系，不要直接更改生产 Key。

## 5. Subscriber Key 与系统内部 ID

| 名称 | 用途 |
|---|---|
| Subscriber Key | 业务层面识别 Subscriber |
| Subscriber ID | Engagement 内部 Subscriber 记录标识 |
| Contact Key | 业务层面识别 Contact |
| Contact ID | Engagement 内部 Contact 记录标识 |

不要把 Subscriber ID / Contact ID 当成跨系统业务主键。Salesforce Contact ID / Lead ID 经 Marketing Cloud Connect 转换后的格式也要按官方集成规则处理。

## 6. Key 设计原则

推荐：
1. 来源于稳定的 CRM Customer ID、Member ID 或系统生成 GUID。
2. 在整个 Enterprise 范围保持唯一，避免不同 BU 或系统意外复用相同值。
3. 不包含会变更的 Email、手机号、姓名等联系信息。
4. 使用 Text 字段，保证格式一致。
5. 定义匿名身份、合并客户、删除后重建等场景的规则。
6. 对导入、API、Journey Entry 和 DE 统一使用相同的映射规则。

## 7. 变更 Key 的风险

把 A 改成 B，通常不应当理解为“更新一个普通字段”。系统可能把 B 识别为新 Subscriber，而 A 的历史状态、追踪和订阅记录仍然存在。

变更前评估：
- 历史发送和 Tracking 如何关联。
- A 是否有 Unsubscribed / Held 状态。
- B 是否已存在。
- 多 BU 是否使用同一个 Key。
- Contact Model / Journey / DE / API 是否依赖旧值。
- 订阅许可和 Consent 如何迁移。

## 8. 常见问题

### 一个 Email 地址可以有多个 Subscriber Key 吗？
可以。系统按 Subscriber Key 区分 Subscriber，而不是仅按 Email Address 去重。具体发送名单是否去重，取决于发送上下文和使用的 Key。

### Subscriber Key 可以是数字吗？
可以将数字业务 ID 作为文本保存；不要把数值型字段直接作为 Contact Key 关系键。建议在数据模型中统一使用 Text。

### 可以直接用 Email 做 Key 吗？
技术上可能，但 Salesforce 建议避免。Email 变更会造成身份连续性问题。

## 9. 本页 Checklist

- [ ] Key 来源、格式和唯一范围已定义。
- [ ] 不依赖 Email / 手机号等可变字段。
- [ ] DE、Import、API 和发送使用相同映射。
- [ ] 与 Contact Key 的关系已明确。
- [ ] Key 变更有迁移和退订风险评估。
