# 06. Contact Key 与数据关系

## 学习目标
掌握 Contact Key、Subscriber Key、Contact ID 的区别，以及它们如何影响 DE、发送、Journey 和多渠道关联。

## 1. 三种标识
| 标识 | 作用 |
|---|---|
| Contact Key | 跨渠道关联同一 Contact 的业务标识 |
| Subscriber Key | Email Studio 中识别 Subscriber 的标识，通常与 Contact Key 对应 |
| Contact ID | 平台内部系统生成的 Contact 标识 |

## 2. 设计原则
Contact Key 应稳定、唯一、不可轻易变更，并在 Email、Mobile、Push、API、Journey 和 Contact Builder 中保持一致。Email Address、手机号和姓名可能变化，不适合作为默认统一标识。

## 3. Sendable DE
Sendable Data Extension 需要定义正确的 Send Relationship，将 DE 中的字段关联到 Subscribers。发送关系选错会造成发送对象关联错误，也可能影响 Contact Key / Subscriber Key 的识别。

## 4. 常见风险
- 同一个人使用多个 Key：形成多个 Contact，跨渠道历史分散。
- 多个人共享一个 Email：若业务需要分别识别，应使用不同 Contact Key。
- 以 Email 作为 Key：邮箱变更时身份关联断裂。
- 导入临时或随机 Key：可能造成 Contact 数量快速增长。
- 修改既有 Key：可能无法自动合并历史 Contact，应先设计迁移和去重方案。

## 5. 设计与迁移步骤
1. 盘点各源系统主键。
2. 定义全局 Contact Key 映射规则。
3. 对比 Email / Mobile / CRM 中的标识。
4. 验证 DE 主键和 Sendable Relationship。
5. 用测试 Contact 验证发送、Journey 和跨渠道关联。
6. 对历史 Key 变更制定数据迁移、重复 Contact 清理和回退方案。

## 常见问题
**Subscriber Key 与 Contact Key 一定相同吗？** 在典型 Email Studio 与 Contact Builder 关系中，Subscriber Key 会成为 Contact Key 使用的标识；设计时应保持一致，但需检查实际账号配置。

**为什么同一邮箱出现多个 Contact？** 因为 Contact 身份主要由 Contact Key 确定，不是只按邮箱地址合并。

## Checklist
- [ ] 全局 Contact Key 规范有文档
- [ ] 所有渠道使用一致映射
- [ ] Sendable Relationship 正确
- [ ] 共享邮箱/多身份场景已考虑
- [ ] Key 变更有迁移计划
