# 02. 日本客户的阅读习惯与思考方式

*日语：日本のお客様の読み方と考え方*

## 本章学习目标

完成本章后，你能够：
- 先定义阅读者是谁、需要完成什么任务，而不是凭印象判断“日本人喜欢什么”。
- 根据阅读者的角色和知识背景调整信息深度。
- 安排标题、结论、流程、条件、补充说明和注意事项的优先级。
- 用清楚的阅读顺序和统一术语减少误解。
- 检查说明图是否回答了客户最关心的问题。

## 1. 先理解“日本客户视角”是什么意思

“日本客户视角”不是把所有日本读者看成同一种人，也不是简单地使用敬语、红色或蓝色模板。真正要做的是确认具体阅读者的工作角色、业务知识、系统知识、决策权限、阅读场景，以及看完资料后需要采取的行动。

例如，同一张数据连携图：
- 业务负责人通常先关心业务何时发生、影响哪些业务、处理结果是什么。
- 系统负责人通常关心系统边界、接口、数据方向、处理条件和异常处理。
- 运维人员通常关心监控、日志、失败后的操作和联系对象。
- 项目经理通常关心范围、依赖关系、责任分工和风险。

因此，制作前先写下“谁看、为什么看、看完要做什么”。

## 2. 日本企业资料中值得采用的阅读原则

以下是适用于多数商务资料的实用原则，并非对所有日本企业或个人的绝对概括。客户指定格式和项目惯例优先。

### 2.1 让主题和范围容易确认

标题应说明对象和内容，不要只写“概要”“关于处理”这类宽泛词语。

| 不够明确 | 更明确的写法 | 为什么 |
|---|---|---|
| 処理概要 | ユーザーデータ連携処理の概要 | 指明对象和处理 |
| システムについて | 対象システムの構成と連携範囲 | 指明说明范围 |
| 注意事項 | データ取込時の注意事項 | 指明注意事项发生在哪个环节 |

### 2.2 先给阅读者定位，再展示细节

页面开头应让读者知道：
- 这张图说明什么。
- 适用哪个系统、业务或处理范围。
- 图中缩写和颜色是否有特殊含义。
- 哪些内容属于本图范围之外。

例如：

~~~text
対象：ユーザーデータ連携処理
範囲：外部システムから連携先システムへのデータ登録
対象外：連携先システム内の後続業務処理
~~~

如果范围尚未确认，应标记「要確認」，不要把推测写成事实。

### 2.3 使用可预测的阅读顺序

常见的安排方式：
- 流程：从左到右，或从上到下，整张图保持一致。
- 判断：先展示判断条件，再分开画出结果。
- 系统结构：按系统边界、层级或职责分组。
- 对比：左右两栏使用相同维度比较。
- 操作步骤：按用户实际操作顺序编号。

不要让箭头交叉、回折或突然改变方向，除非业务本身确实存在循环或返回。

## 3. 用“读者问题”决定信息顺序

可使用以下问题检查内容是否完整：

| 读者可能提出的问题 | 说明图中应出现的信息 |
|---|---|
| 这张图讲什么？ | 标题、对象、范围 |
| 从哪里开始？ | 起点、触发条件 |
| 谁或哪个系统负责？ | 角色、系统边界、责任 |
| 中间发生什么？ | 处理步骤、数据传递 |
| 为什么走这条分支？ | 判断条件、条件定义 |
| 结果是什么？ | 输出、状态、业务结果 |
| 出错怎么办？ | 异常处理、日志、通知、恢复方式（仅限已确认内容） |
| 哪些内容不在范围内？ | 范围外说明、前提条件 |

不要为了让图“看起来完整”而回答资料没有定义的问题。未知信息应列为确认事项。

## 4. 信息层级：主线、条件、补充和注意

建议把信息分成四层：

1. **主线信息**：读者必须理解的主要步骤或关系。
2. **条件信息**：决定处理分支的条件、前提和限制。
3. **补充信息**：字段例子、时间、备注、术语解释。
4. **注意信息**：风险、未确认事项、操作限制。

主线应最容易看到；条件紧贴相关步骤；补充信息可放在旁注或图例；注意事项放在对应位置，不要集中堆在页面角落让读者找不到。

### 示例：把一段文字分层

原文：

~~~text
每天凌晨从外部系统取得用户数据，检查必填字段。检查通过后注册到目标系统。检查失败时记录日志并通知负责人。处理时间可能因数据量而变化。
~~~

整理：

| 层级 | 信息 |
|---|---|
| 主线 | 数据取得 → 必填字段检查 → 目标系统注册 |
| 条件 | 必填字段是否完整 |
| 异常 | 记录错误日志、通知负责人 |
| 补充 | 每天凌晨执行 |
| 注意 | 处理时间可能随数据量变化 |

“处理时间可能因数据量而变化”应作为补充或注意，不要误画成流程判断条件。

## 5. 日语商务资料的表达习惯

### 5.1 一句话表达一个动作或判断

不推荐：

~~~text
データを取得した後、必須項目の確認を行い、問題がなければ登録処理を実施します。
~~~

图中可简化为：

~~~text
データ取得
必須項目チェック
連携先へ登録
~~~

详细说明可放在图外的备注中。缩短文字时不能删掉决定业务含义的条件。

### 5.2 统一术语和称呼

同一对象不要在一张图中随意交替使用「ユーザー」「会員」「顧客」；如果它们是不同业务实体，应明确区分。项目术语表、设计书和客户指定用语优先。

### 5.3 明确主语和责任

「データを更新する」可能没有说明由谁更新。可根据已确认事实写成「連携先システムがデータを更新する」。如果执行主体不明，应列为确认事项，而不是擅自补充。

## 6. 让读者更容易理解的版面方法

- 标题放在固定且明显的位置。
- 同一层级的处理框保持相近尺寸。
- 同类对象使用一致的颜色和形状。
- 箭头尽量不交叉。
- 重要条件放在判断节点附近。
- 图例靠近图形或放在固定区域。
- 不要把长段落塞进流程框；详细说明放在旁注或配套表格。

## 7. 实际案例：同一内容面向不同读者

说明对象：外部系统向目标系统传送用户数据。

| 读者 | 应重点展示 | 不宜过度强调 |
|---|---|---|
| 业务负责人 | 执行时机、业务结果、影响范围 | API 参数和技术字段细节 |
| 系统负责人 | 系统边界、数据方向、检查条件、错误处理 | 与本次说明无关的业务背景 |
| 运维人员 | 监控点、日志、异常通知、恢复步骤 | 未涉及的业务决策背景 |
| 项目经理 | 范围、依赖、责任、风险 | 过细的字段定义 |

同一事实可以有不同展示深度，但不能因读者不同而改变业务事实。

## 8. 实际练习

### 练习 A：定义阅读者

假设客户要求说明“申请审批流程”。分别写出业务负责人、系统负责人和操作人员最想确认的三个问题。

### 练习 B：信息分层

将以下信息分类为主线、条件、补充或注意：

- 用户提交申请。
- 系统检查必填项目。
- 必填项目不完整时提示补充。
- 申请提交时间为工作日 9:00～18:00（假设资料已明确）。
- 审批通过后状态变为「承認済み」。
- 审批失败时状态变为「否認」。

### 练习 C：修改标题

把「処理について」「システム概要」「注意事項」改成能够体现对象和范围的标题。

## 9. 完成标准

- [ ] 能说清楚目标阅读者和阅读目的。
- [ ] 能列出不同角色关心的问题。
- [ ] 能区分主线、条件、补充和注意信息。
- [ ] 标题能说明对象和内容。
- [ ] 阅读顺序明确，箭头方向一致。
- [ ] 术语统一，责任主体清楚。
- [ ] 未确认内容没有被写成确定事实。

**达标成果：** 为“申请审批流程”制作一份读者分析表和信息分层表，并说明为什么这样安排。

## 10. 本章总结

日本客户视角的核心不是套用刻板印象，而是围绕具体阅读者的任务组织信息。先明确谁看、为什么看、看完要做什么，再决定标题、信息层级、阅读顺序和说明深度。
