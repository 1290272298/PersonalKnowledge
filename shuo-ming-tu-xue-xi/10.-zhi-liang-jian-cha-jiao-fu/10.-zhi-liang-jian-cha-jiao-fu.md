# 10. 质量检查与交付标准

## 本章学习目标

- 从事实、逻辑、日语、视觉和交付五个方面检查说明图。
- 区分必须修正的问题和可选优化。
- 通过客户视角检查图是否容易理解。
- 正确保存源文件、导出文件和版本记录。
- 使用标准 Checklist 判断是否可以交付。

## 1. 质量检查的五个维度

| 维度 | 核心问题 | 典型错误 |
|---|---|---|
| 业务事实 | 图中的信息是否真实、已确认？ | 自行补充规则 |
| 逻辑结构 | 步骤、条件和关系是否正确？ | 分支遗漏、箭头错误 |
| 日语表达 | 文字是否准确、自然、统一？ | 术语不一致、条件含糊 |
| 视觉可读性 | 是否容易阅读和追踪？ | 字体太小、线条交叉 |
| 交付管理 | 文件、版本和格式是否正确？ | 源文件缺失、版本不一致 |

## 2. 业务事实检查

逐项对照原始资料：
- 系统名称、模块名称和角色名称是否准确？
- 数据对象、字段名称和状态值是否与项目定义一致？
- 处理步骤是否有资料依据？
- 处理时间、执行频率和触发条件是否准确？
- 数据来源和目标是否正确？
- 异常处理、通知方式和重试规则是否已经确认？
- 是否把推测写成事实？
- 是否超出本图说明范围？

没有资料依据的内容应删除或标记「要確認」，不能因为图看起来不完整而自行补充。

## 3. 逻辑完整性检查

流程图：
- 是否有明确起点和终点？
- 每一步是否有合理的前后关系？
- 判断节点是否写明条件？
- 每个判断分支是否有明确去向？
- 是否遗漏本次范围内的重要异常路径？
- 是否存在没有输入的处理或没有去向的结果？
- 循环、并行和汇合是否表达准确？

系统结构图：
- 系统边界是否明确？
- 模块层级是否合理？
- 连接线代表什么关系？
- 是否误把关联画成调用顺序？

数据流向图：
- 数据来源和目标是否清楚？
- 箭头方向是否正确？
- 数据名称是否标注？
- 转换或加工位置是否准确？
- 是否把未确认的接口方式写入图中？

## 4. 日语和术语检查

- 标题能否说明对象和内容？
- 一个流程框是否只表达一个主要动作？
- 判断条件是否能明确回答？
- 主语或执行主体是否需要补充？
- 系统名称、字段名、状态值是否保持原样？
- 同一概念是否使用同一个术语？
- 缩写是否在首次出现时解释？
- 是否有中文直译、错字、标点或不自然表达？
- 是否因为缩短句子而丢失条件或限制？

客户指定术语表优先。AI 的日语修改建议也必须人工确认。

## 5. 视觉可读性检查

- 标题是否明显？
- 阅读方向是否清楚？
- 主流程是否容易追踪？
- 图形、箭头和颜色的含义是否一致？
- 文字在最终展示尺寸下是否容易阅读？
- 同类节点是否对齐、大小相近？
- 是否有不必要的装饰？
- 颜色是否有文字或形状辅助？
- 图例是否完整？
- 是否存在箭头交叉、文字重叠或边界不清？

将页面缩小到实际演示比例，或导出 PDF 后检查。只在编辑画布放大状态下看起来清楚，并不代表最终交付清楚。

## 6. 日本客户视角的最终确认

站在第一次看到这张图的读者角度，回答：
1. 我能否快速知道这张图说明什么？
2. 我是否知道图的适用范围？
3. 我知道从哪里开始阅读吗？
4. 我能看懂每一步由谁或哪个系统执行吗？
5. 我能理解判断条件和不同结果吗？
6. 我能区分已确认内容和待确认内容吗？
7. 我知道图中缩写、颜色和线条代表什么吗？
8. 如果需要采取行动，我知道下一步是什么吗？

如果读者必须依赖制作人现场解释才能理解，说明图还需要改善。

## 7. 问题优先级

| 优先级 | 问题类型 | 处理方式 |
|---|---|---|
| 必须修正 | 事实错误、逻辑错误、错误数据方向 | 交付前必须修正 |
| 必须确认 | 业务条件未定义、责任主体不明 | 找负责人确认 |
| 应修正 | 术语不统一、关键说明遗漏、阅读顺序不清 | 原则上交付前修正 |
| 可优化 | 颜色细节、非关键间距、装饰细节 | 时间允许时改善 |

不要先花时间调整颜色，却忽略业务逻辑错误。

## 8. 文件和交付检查

交付前确认：
- 文件名符合客户或公司规范。
- 文件版本和更新日期正确。
- 可编辑源文件已保存。
- 导出 PDF 或图片与源文件内容一致。
- 字体、换行、图片和图形没有错位。
- 文件可以正常打开。
- 不包含隐藏的草稿、个人信息或不应交付的备注。
- 交付范围和接收对象正确。
- 如项目要求，附上修改记录或确认记录。

文件名示例：

~~~text
案件名_資料名_YYYYMMDD_v01.pptx
案件名_資料名_YYYYMMDD_v01.pdf
~~~

示例名称应替换成项目允许使用的名称，并遵循客户文件命名规则。

## 9. 可复用的最终自检表

### 内容和事实
- [ ] 制作目的和阅读对象明确。
- [ ] 图的说明范围明确。
- [ ] 主要信息均有资料依据。
- [ ] 系统名、数据名、状态值准确。
- [ ] 未确认内容已标记或删除。
- [ ] 没有擅自增加业务规则。

### 逻辑
- [ ] 处理步骤顺序正确。
- [ ] 判断条件明确。
- [ ] 分支结果和去向完整。
- [ ] 正常和异常处理符合本次说明范围。
- [ ] 数据流向和系统关系正确。
- [ ] 没有逻辑断点或错误箭头。

### 日语
- [ ] 标题明确。
- [ ] 句子简洁、自然。
- [ ] 术语和缩写统一。
- [ ] 主语、责任主体和条件清楚。
- [ ] 没有错字和不必要的长句。

### 视觉
- [ ] 阅读顺序明确。
- [ ] 字体和字号易读。
- [ ] 颜色含义一致且有文字辅助。
- [ ] 图形和箭头样式统一。
- [ ] 元素对齐，间距合理。
- [ ] 图例和注释完整。
- [ ] 无文字重叠或线条交叉造成的误读。

### 交付
- [ ] 文件名和版本正确。
- [ ] 源文件已保存。
- [ ] PDF/图片导出正常。
- [ ] 导出结果与源文件一致。
- [ ] 文件可正常打开。
- [ ] 无不应交付的机密或个人信息。
- [ ] 符合客户指定的交付格式。

## 10. 最终交付判断

只有在事实和逻辑问题已解决、必要的待确认事项已得到处理或明确标记、日语和视觉检查通过、文件和版本正确时，才可以进入交付。

若仍有未解决的业务问题，不要把资料标记为“最终确定版”。应明确标注版本状态，例如「レビュー用」「確認中」「最終版」，并按项目规则使用。

## 11. 课程最终实战验收

请拿出第 09 章完成的三份作品：
1. 业务处理流程图。
2. 系统数据连携图。
3. 系统操作说明图。

分别使用本章 Checklist 检查。每张图记录至少一项自检结果；如果没有发现问题，也应记录检查结论和检查日期。

**课程完成标准：**
- [ ] 三份作品都完成自检。
- [ ] 必须修正的问题已处理。
- [ ] 未确认事项已明确标注。
- [ ] 源文件和交付文件齐全。
- [ ] 能向他人说明制作依据、图形结构和质量检查结果。

## 12. 本章总结

交付不是“图画完了”就结束。必须确认事实准确、逻辑完整、日语清楚、视觉可读、文件正确。质量检查应在制作过程中持续进行，最后再做一次完整复核。
