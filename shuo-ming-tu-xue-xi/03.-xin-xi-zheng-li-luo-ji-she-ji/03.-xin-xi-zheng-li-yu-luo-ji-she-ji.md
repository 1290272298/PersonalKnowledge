# 03. 说明内容的整理与逻辑设计

## 本章学习目标

- 从原始资料提取对象、触发、动作、条件、结果和责任主体。
- 区分已确认事实、推测和待确认事项。
- 把长段文字拆成步骤和判断关系。
- 在绘图之前形成可供确认的逻辑草稿。
- 检查异常分支、输入输出和逻辑断点。

## 1. 为什么必须先整理逻辑

绘图工具只能表达信息，不能替你判断业务。原始信息不完整时，直接画图容易把推测画成事实。推荐顺序：

~~~text
原始资料 → 信息提取 → 逻辑整理 → 待确认事项 → 草图 → 正式绘制
~~~

## 2. 从原始资料提取六类信息

| 类别 | 要回答的问题 | 示例 |
|---|---|---|
| 对象 | 谁或什么参与？ | 用户、外部系统、目标系统 |
| 触发 | 什么情况下开始？ | 每天凌晨、用户提交 |
| 动作 | 执行什么处理？ | 取得、检查、注册 |
| 条件 | 根据什么判断？ | 必填字段是否完整 |
| 结果 | 处理后发生什么？ | 注册完成、错误记录 |
| 责任 | 谁负责执行或处理？ | 应用系统、担当者 |

同时记录时间、频率、输入输出、状态、限制条件和信息来源。

## 3. 将原文拆成事实清单

原文：

~~~text
用户提交申请后，系统检查必填信息。信息完整时进入审批流程；信息不完整时提示用户补充。审批通过后状态更新为承認済み，未通过时更新为否認。
~~~

整理表：

| ID | 条件/顺序 | 执行主体 | 动作 | 结果 |
|---|---|---|---|---|
| F-01 | 用户发起 | 用户 | 提交申请 | 申请已提交 |
| F-02 | 提交后 | 系统 | 检查必填信息 | 检查结果 |
| F-03 | 信息完整 | 系统 | 进入审批流程 | 进入审批 |
| F-04 | 信息不完整 | 系统 | 提示补充 | 等待补充 |
| F-05 | 审批通过 | 系统 | 更新状态 | 承認済み |
| F-06 | 审批未通过 | 系统 | 更新状态 | 否認 |

事实 ID 用于评审时追溯，不一定放进客户最终图中。

## 4. 区分事实、推测和待确认事项

| 分类 | 判断依据 | 处理方式 |
|---|---|---|
| 已确认事实 | 原始资料明确记载或负责人确认 | 可以写入 |
| 推测 | 根据上下文推断，尚未确认 | 不直接画成事实 |
| 待确认 | 资料未定义或不同资料冲突 | 标记「要確認」 |
| 范围外 | 本图不负责说明 | 标记「対象外」 |

例如，资料写“错误时通知负责人”，但没有写通知渠道。应记录：

~~~text
要確認：通知方式（メール／画面通知／その他）
~~~

不能自行画成“发送邮件”。

## 5. 识别动作词和条件词

常见动作词：取得する、登録する、更新する、削除する、連携する、確認する、通知する、出力する。

常见条件表达：
- ～の場合：在……情况下
- ～であれば：如果……
- ～かどうか：是否……
- ～に該当する：符合……
- ～を満たす：满足……

把“数据正常吗？”改成可验证的条件，例如「必須項目がすべて設定されているか」。

一个流程框尽量只写一个主要动作。多个动作存在先后关系时，应拆成多个步骤。

## 6. 识别对象之间的逻辑关系

| 关系 | 含义 | 图形表达 |
|---|---|---|
| 顺序 | A 后执行 B | 流程箭头 |
| 分支 | 条件不同，结果不同 | 判断节点 |
| 并行 | A 与 B 可同时发生 | 并行分支 |
| 汇合 | 多条路径回到同一处理 | 汇合节点 |
| 循环 | 重复执行直到条件满足 | 回路线 |
| 关联 | 对象之间存在关系，不代表先后 | 关系线 |
| 数据传递 | 数据从一处流向另一处 | 带方向的数据箭头 |

不要把一般关联误画成执行顺序。

## 7. 先写伪流程，再画图

申请审批案例：

~~~text
开始
  用户提交申请
  系统检查必填信息
  判断：必填信息是否完整？
    是：进入审批流程
    否：提示用户补充信息
  审批完成后判断审批结果
    通过：状态更新为承認済み
    未通过：状态更新为否認
结束
~~~

先让业务负责人确认伪流程，再转换成正式图形，通常更容易发现遗漏。

## 8. 使用输入—处理—输出检查完整性

| 环节 | 检查问题 |
|---|---|
| 输入 | 数据或操作从哪里来？谁发起？ |
| 处理 | 系统执行什么动作？顺序是什么？ |
| 判断 | 判断依据和分支结果是否明确？ |
| 输出 | 产生什么数据、状态或通知？ |
| 责任 | 谁负责执行、确认或处理异常？ |

检查是否有“没有输入来源的处理框”或“没有去向的结果”。

## 9. 异常和边界条件检查

阅读资料时逐项确认：
- 输入为空或格式错误时如何处理？
- 重复提交时如何处理？
- 处理超时或连接失败时如何处理？
- 部分成功时如何处理？
- 是否允许重试？重试次数和条件是什么？
- 是否存在取消、撤回或人工介入？

这些是检查问题，不代表系统一定存在这些处理。必须根据资料或负责人确认后再画入正式图。

## 10. 实际练习

原文：

~~~text
每天 8:00，系统读取前一天的订单数据。读取后检查订单状态。状态为「確定」的数据写入分析系统，其他状态的数据不写入，并统计未写入件数。
~~~

请完成：
1. 整理对象、触发时间、动作和判断条件。
2. 写出正常结果和其他结果。
3. 说明统计结果属于主流程还是补充信息。
4. 列出原文未说明的内容。
5. 写出不超过 10 行的伪流程。

## 11. 完成标准

- [ ] 能提取对象、触发、动作、条件、结果和责任。
- [ ] 关键事实可以追溯到来源。
- [ ] 能区分事实、推测和待确认事项。
- [ ] 能识别顺序、分支、并行、汇合和循环。
- [ ] 能写出逻辑完整的伪流程。
- [ ] 能用输入—处理—输出检查完整性。
- [ ] 没有擅自添加未定义处理。

**达标成果：** 提交事实清单、待确认事项清单和伪流程。

## 12. 本章总结

先提取事实，再建立关系；先确认条件，再决定如何绘制。图形是逻辑的表达，不是逻辑本身。
