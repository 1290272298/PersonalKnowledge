# 01. 说明图制作基础知识

*日语：説明図・図解の基礎知識*

## 1. 本章学习目标

完成本章后，你应该能够：

- 理解什么是说明图。
- 区分说明图、普通 PPT 和操作手册。
- 理解日本企业在什么情况下需要说明图。
- 判断一份说明资料是否适合制作成图。
- 掌握从准备资料到完成说明图的基本流程。
- 初步判断一张说明图是否容易被日本客户理解。

**本章重点：不是学习如何把图画得漂亮，而是学习如何把复杂的信息清楚地传达给别人。**

---

## 2. 什么是说明图？

### 2.1 基础概念

说明图（日语：説明図、図解）是将文字、业务流程、系统关系、数据流向等信息，通过图形、箭头、文字和颜色等方式进行整理和展示，让阅读者能够快速理解内容的一种表达方式。

简单来说：

**说明图 = 信息整理 + 逻辑关系 + 视觉表达**

例如，需要向客户说明一个系统的数据处理过程。

只用文字说明：

> 系统从外部数据源获取用户数据，经过数据检查后，将符合条件的数据导入目标系统。如果数据不符合要求，则记录错误信息，并通知相关人员。

这段文字虽然说明了处理过程，但是阅读者需要自己在脑海中整理步骤和关系。

如果整理成图：

~~~text
外部データ
    │
    ▼
データ取得
    │
    ▼
データチェック
    │
    ▼
条件を満たしているか？
    │
  ┌─┴─┐
  │   │
 YES  NO
  │   │
  ▼   ▼
データ  エラーログ
取込    記録
  │   │
  ▼   ▼
処理完了  担当者へ通知
~~~

阅读者就可以直接看到：

- 数据从哪里来。
- 系统执行了什么操作。
- 在哪个位置进行判断。
- 判断结果不同会发生什么。
- 正常处理和异常处理分别是什么。

这就是说明图的价值。

### 2.2 说明图不等于装饰图片

说明图的主要目的不是美化页面，而是帮助阅读者理解信息。

| 内容 | 主要目的 |
|---|---|
| 装饰图片 | 让页面更美观 |
| 普通 PPT | 展示文字、数据和演讲内容 |
| 操作手册 | 指导用户一步一步执行操作 |
| 说明图 | 展示信息、流程、结构和逻辑关系 |

一张图即使使用了很多颜色、图标和动画，如果无法让客户理解业务内容，也不能算是一张合格的说明图。

### 2.3 日本商务场景中常见的说明图名称

在日本企业的资料中，可能会看到以下表达：

| 日语 | 中文含义 | 常见用途 |
|---|---|---|
| 説明図 | 说明图 | 解释某项内容 |
| 概念図 | 概念图 | 说明整体概念 |
| 業務フロー図 | 业务流程图 | 说明业务处理顺序 |
| システム構成図 | 系统结构图 | 说明系统组成 |
| データフロー図 | 数据流向图 | 说明数据传递关系 |
| 処理フロー図 | 处理流程图 | 说明系统处理步骤 |
| 操作手順図 | 操作步骤图 | 说明操作方法 |
| 比較図 | 对比图 | 展示新旧差异或方案差异 |
| 関連図 | 关系图 | 展示对象之间的关系 |

注意：这些名称的具体使用范围可能因公司和项目而异。制作之前，最好确认客户或项目中使用的资料名称。

## 3. 为什么日本企业需要说明图？

### 3.1 减少阅读者理解信息的时间

当一份资料包含大量文字时，阅读者需要自己寻找重点、判断顺序、理解条件之间的关系。

通过说明图，可以把这些信息整理成更容易阅读的结构。

例如：

**文字表达**

~~~text
用户登录系统后，系统会检查用户的权限。
如果用户拥有管理员权限，则可以进入管理页面。
如果用户没有管理员权限，则只能进入普通用户页面。
~~~

**图形表达**

~~~text
        ユーザーがログイン
                │
                ▼
          権限チェック
                │
         ┌──────┴──────┐
         ▼             ▼
    管理者権限あり   管理者権限なし
         │             │
         ▼             ▼
     管理画面へ      一般画面へ
~~~

两种表达都可以传达相同的信息，但图形表达更容易展示判断条件和分支关系。

### 3.2 减少理解偏差

在系统开发、业务设计和项目沟通中，不同人员可能对同一段文字产生不同理解。

例如：

> データ連携後、対象データを更新する。

这句话可能产生以下疑问：

- 哪个系统负责更新？
- 更新哪些数据？
- 是新增还是覆盖？
- 什么情况下执行更新？
- 更新失败后如何处理？

说明图可以把系统、数据、处理条件和处理结果分别展示出来。

但要注意：

**说明图不能自动消除业务定义中的模糊内容。**

如果原始资料没有明确说明更新条件，就不能为了让图看起来完整而自行补充业务规则。

### 3.3 方便会议和项目沟通

日本企业项目中，经常需要向不同角色说明同一项内容，例如客户负责人、项目经理、业务负责人、系统工程师、运维人员和测试人员。

这些人员关注的内容不一定相同。

例如，说明一个数据连携流程：

| 阅读者 | 可能重点关注的内容 |
|---|---|
| 客户负责人 | 整体流程、业务影响 |
| 项目经理 | 处理范围、依赖关系、进度 |
| 系统工程师 | 系统接口、数据流向、处理条件 |
| 运维人员 | 错误处理、日志、异常通知 |
| 测试人员 | 输入条件、处理结果、异常分支 |

因此，在制作说明图之前，必须先明确：

**这张图是给谁看的？希望对方看完后理解什么？**

### 3.4 便于后续维护和交接

如果系统处理逻辑只记录在个人的说明文字中，后续人员可能很难理解整体关系。

通过说明图，可以更直观地展示系统之间的关系、业务处理顺序、数据的输入和输出、正常处理与异常处理，以及各处理步骤的责任范围。

这样有助于项目交接、系统维护和后续设计变更。

## 4. 什么情况下应该制作说明图？

并不是所有内容都需要制作成图。

| 内容类型 | 推荐表达方式 | 原因 |
|---|---|---|
| 多个步骤依次执行 | 流程图 | 需要展示先后顺序 |
| 多个系统之间传递数据 | 数据流向图 | 需要展示传递方向 |
| 系统由多个模块组成 | 系统结构图 | 需要展示组成关系 |
| 多个条件决定不同结果 | 判断流程图 | 需要展示分支 |
| 新旧系统存在差异 | 对比图 | 需要突出差异 |
| 只有一个简单定义 | 文字说明 | 没有必要强行画图 |
| 大量详细参数 | 表格 | 方便逐项比较 |
| 需要逐步执行操作 | 操作步骤图或操作手册 | 需要指导用户操作 |

### 4.1 一个简单的判断方法

拿到一份业务资料时，可以先问自己：

1. 是否存在多个处理步骤？
2. 是否存在先后顺序？
3. 是否存在系统之间的关系？
4. 是否存在数据传递？
5. 是否存在条件判断？
6. 是否需要展示正常和异常处理？
7. 是否需要比较多个对象？

如果其中一项或多项符合，可以考虑使用说明图。

如果内容只是一个简单定义或单独的注意事项，直接使用文字可能更合适。

## 5. 一张合格的说明图应该具备什么？

从日本客户的阅读视角来看，一张说明图至少需要满足以下要求。

### 5.1 一眼能够理解主题

阅读者应该能够通过标题，知道这张图说明什么。

不推荐：

~~~text
処理について
~~~

推荐：

~~~text
ユーザーデータ連携処理の概要
~~~

原因：

第一个标题范围太广，阅读者不知道具体说明什么。第二个标题明确指出了说明对象和内容。

### 5.2 阅读顺序明确

阅读者应该能够知道从哪里开始看、接下来查看哪里。

常见布局：

- 横向：从左到右。
- 纵向：从上到下。
- 判断分支：从判断节点向不同方向展开。
- 系统结构：按照系统层级或功能关系组织。

例如：

~~~text
① データ取得
      ↓
② データチェック
      ↓
③ データ登録
      ↓
④ 処理完了
~~~

不要随意安排箭头方向，也不要让阅读者需要反复寻找下一步。

### 5.3 信息之间的关系明确

图中的元素不能只是简单地放在一起，必须让阅读者知道它们之间是什么关系。

例如：

- 箭头：表示流程方向或数据传递方向。
- 方框：表示处理步骤或系统模块。
- 菱形：表示条件判断。
- 虚线：可以表示参考关系或非主要流程，但必须在图例中解释。
- 颜色：可以用于区分系统、状态或处理类别，但必须保持含义一致。

图形符号的含义应在同一张图中保持一致。如果使用了特殊符号，最好添加图例。

### 5.4 日语表达准确、简洁

说明图中的日语不应过于复杂。

不推荐：

~~~text
データの取得を行った後に、取得されたデータに対して内容の確認を実施し、問題がない場合には登録処理を実施する。
~~~

推荐：

~~~text
① データ取得
② データチェック
③ データ登録
~~~

原因：

- 每个步骤只表达一个主要动作。
- 阅读者可以快速识别处理内容。
- 减少重复表达。
- 更适合放在图形中。

如果涉及重要条件或例外情况，应另外补充说明，不能为了缩短文字而删除必要信息。

### 5.5 正常处理和异常处理都要考虑

例如：

~~~text
        データチェック
              │
       ┌──────┴──────┐
       ▼             ▼
    正常             異常
       │             │
       ▼             ▼
    データ登録    エラーログ記録
                     │
                     ▼
                  担当者へ通知
~~~

如果只画正常处理，客户可能会进一步询问数据错误时怎么办、处理失败后是否会重新执行、是否会记录日志、是否会通知负责人。

但并不是每张图都必须展示所有异常情况。应根据说明目的和客户要求决定展示范围。

### 5.6 不依赖颜色也能理解

颜色可以帮助区分信息，但不能只依靠颜色传达重要含义。

例如：

- 不要只用红色和绿色区分错误与正常。
- 可以同时使用「正常」「異常」文字。
- 可以搭配图标或不同形状。

这样即使打印成黑白资料，阅读者也能理解。

## 6. 从零开始制作说明图的基本流程

初学者最容易犯的错误，是拿到资料后马上打开 PowerPoint 或 draw.io 开始画图。

正确的做法是先整理信息，再设计结构，最后制作图形。

### 6.1 整体制作流程

~~~text
① 确认制作目的
        ↓
② 确认阅读对象
        ↓
③ 收集和阅读原始资料
        ↓
④ 整理必要信息
        ↓
⑤ 确定说明图类型
        ↓
⑥ 设计图形结构
        ↓
⑦ 编写日语说明文字
        ↓
⑧ 使用工具制作
        ↓
⑨ 检查业务逻辑和日语
        ↓
⑩ 从客户视角检查
        ↓
⑪ 导出并交付
~~~

### 6.2 每一步具体应该做什么？

| 步骤 | 应该做什么 | 完成后的结果 |
|---|---|---|
| ① 确认制作目的 | 明确为什么需要这张图 | 制作目的 |
| ② 确认阅读对象 | 明确谁会阅读 | 阅读对象 |
| ③ 收集资料 | 收集设计书、业务说明、系统资料等 | 原始资料 |
| ④ 整理信息 | 提取处理步骤、条件、关系 | 信息清单 |
| ⑤ 确定图类型 | 判断使用流程图、结构图或其他图 | 图类型 |
| ⑥ 设计结构 | 确定布局、箭头和信息顺序 | 草图 |
| ⑦ 编写日语 | 编写标题、步骤和注意事项 | 日语文案 |
| ⑧ 使用工具制作 | 通过 draw.io 或 PowerPoint 绘制 | 初版说明图 |
| ⑨ 检查逻辑和日语 | 检查事实、条件、术语和表达 | 修正版 |
| ⑩ 客户视角检查 | 判断是否容易理解 | 最终版 |
| ⑪ 导出交付 | 导出 PDF 或 PPTX 等指定格式 | 交付文件 |

### 6.3 第一步：确认制作目的

开始之前，先写出一句话：

> この資料を通じて、何を理解してもらいたいのか。

中文意思：希望阅读者通过这份资料理解什么？

例如：

~~~text
制作目的：
向客户说明用户数据从外部系统传输到目标系统的整体处理流程。
~~~

这句话将成为后续制作的判断标准。

如果制作过程中增加了大量与这个目的无关的信息，就需要考虑是否应该删除或拆分。

### 6.4 第二步：确认阅读对象

例如：

~~~text
阅读对象：
客户的系统负责人。
~~~

那么说明图应该重点展示：

- 系统之间的关系。
- 数据传递方向。
- 主要处理步骤。
- 数据处理条件。
- 异常时的处理方式。

如果阅读对象是业务负责人，则可能需要减少技术细节，突出业务处理结果和影响范围。

### 6.5 第三步：整理原始资料

假设原始资料写着：

~~~text
每天凌晨，系统从外部数据源获取用户数据。
获取后检查必填字段。
如果检查通过，则将数据注册到目标系统。
如果检查失败，则记录错误日志，并通知系统负责人。
~~~

先不要画图，应该先提取信息：

| 项目 | 整理结果 |
|---|---|
| 执行时间 | 每天凌晨 |
| 数据来源 | 外部数据源 |
| 处理 1 | 获取用户数据 |
| 处理 2 | 检查必填字段 |
| 判断条件 | 必填字段是否完整 |
| 正常处理 | 注册到目标系统 |
| 异常处理 | 记录错误日志 |
| 通知对象 | 系统负责人 |

这一步非常重要。如果原始资料中没有明确说明某个条件，就先标记为「要確認」，不要自行推测。

### 6.6 第四步：确定说明图类型

根据刚才整理的信息：

- 存在多个处理步骤。
- 存在先后顺序。
- 存在条件判断。
- 存在正常和异常分支。

因此，适合使用：

**業務フロー図（业务流程图）或処理フロー図（处理流程图）。**

### 6.7 第五步：先设计结构，再使用工具

在真正绘图之前，先用简单的文字或纸笔画出结构。

例如：

~~~text
データ取得
    ↓
必須項目チェック
    ↓
チェック結果
  ┌─┴─┐
  │   │
 正常  異常
  │   │
  ▼   ▼
データ  エラーログ
登録    記録
  │   │
  ▼   ▼
完了  担当者へ通知
~~~

这就是草图。此时不需要考虑颜色、图标、字体或动画，首先确认逻辑是否正确。

### 6.8 第六步：制作并检查

逻辑确认后，再使用绘图工具。

本手册后续会分别介绍：

- draw.io：适合流程图、系统结构图、数据流向图。
- PowerPoint：适合商务说明资料、客户提案和综合页面。
- Figma：适合更精细的视觉设计和组件化管理。
- ChatGPT：适合信息整理、日语文案优化和初步检查。

这些工具的具体操作将在第 07 章详细学习。

## 7. 实际案例：将文字说明转换成说明图

### 7.1 案例背景

假设你正在参与一个系统数据连携项目。客户希望了解用户数据如何从外部系统传递到目标系统，以及数据不符合条件时如何处理。

### 7.2 原始文字

~~~text
每天凌晨，系统从外部系统取得用户数据。
取得的数据需要进行必填字段检查。
检查通过的数据会注册到目标系统。
检查失败的数据会记录错误日志，并通知负责人。
~~~

### 7.3 整理必要信息

| 分类 | 内容 |
|---|---|
| 数据来源 | 外部系统 |
| 数据取得时间 | 每天凌晨 |
| 检查内容 | 必填字段检查 |
| 正常条件 | 必填字段检查通过 |
| 正常结果 | 注册到目标系统 |
| 异常条件 | 必填字段检查失败 |
| 异常结果 | 记录错误日志 |
| 通知对象 | 负责人 |

### 7.4 确定标题

不推荐：

~~~text
データについて
~~~

推荐：

~~~text
ユーザーデータ連携処理の概要
~~~

### 7.5 设计日语步骤

| 中文 | 推荐日语 |
|---|---|
| 获取用户数据 | ユーザーデータ取得 |
| 检查必填字段 | 必須項目チェック |
| 检查通过 | チェックOK |
| 检查失败 | チェックNG |
| 注册到目标系统 | 連携先システムへ登録 |
| 记录错误日志 | エラーログ記録 |
| 通知负责人 | 担当者へ通知 |

### 7.6 完成后的结构示例

~~~text
       ユーザーデータ連携処理の概要

              外部システム
                    │
                    ▼
              ユーザーデータ取得
                    │
                    ▼
              必須項目チェック
                    │
              ┌─────┴─────┐
              ▼           ▼
          チェックOK   チェックNG
              │           │
              ▼           ▼
       連携先システムへ   エラーログ記録
            登録              │
              │               ▼
              ▼           担当者へ通知
           処理完了
~~~

### 7.7 交付前还需要确认什么？

这张图只是根据案例资料制作的示例，并不代表所有项目都可以直接采用。

实际项目中还需要确认：

- 每天凌晨的具体执行时间是否需要展示？
- 是否存在数据重复注册的情况？
- 注册失败时如何处理？
- 是否会自动重新执行？
- 错误日志记录在哪里？
- 通知方式是什么？

原始资料没有定义的内容，应向相关负责人确认后再决定是否加入。

**重要原则：说明图可以整理事实，但不能代替业务确认。**

## 8. 初学者常见误区

| 常见误区 | 为什么不合适 | 正确做法 |
|---|---|---|
| 一拿到资料就开始画图 | 还没有理解业务逻辑 | 先阅读并整理信息 |
| 认为颜色越多越好 | 颜色过多会分散注意力 | 先确定信息层级 |
| 把所有文字都放进图里 | 内容过多，不容易阅读 | 区分主要信息和补充信息 |
| 只画正常流程 | 可能遗漏重要异常情况 | 根据范围确认是否需要异常分支 |
| 日语越长越详细越好 | 图中文字过长会影响阅读 | 使用简洁、准确的表达 |
| 为了美观自行修改业务条件 | 可能导致设计错误 | 业务事实必须以确认资料为准 |
| 认为 AI 生成的图一定正确 | AI 可能误解条件或补充不存在的信息 | 必须人工核对业务内容 |

### 8.1 特别注意：不要为了图形完整而补充未经确认的信息

例如，原始资料只写：

~~~text
エラー発生時、担当者へ通知する。
~~~

不能擅自画成：

~~~text
エラー発生
    ↓
自動再実行
    ↓
再実行失敗
    ↓
メール通知
~~~

因为原始资料没有说明自动重试和邮件通知。

这类问题在系统设计资料中尤其需要注意。

### 练习 1：判断是否需要说明图

请判断下面的内容适合使用哪种表达方式。

| 题目 | 推荐表达方式 |

| 说明用户如何完成页面操作 | 操作步骤图 |

### 练习 2：整理原始业务信息

请阅读下面的内容：

~~~text
用户在系统中提交申请后，系统会检查申请信息。
如果信息完整，则进入审批流程。
如果信息不完整，则提示用户补充信息。
审批通过后，申请状态更新为已批准。
审批未通过时，申请状态更新为已拒绝。
~~~

请自行整理：

1. 数据或操作的起点是什么？
2. 系统执行了什么检查？
3. 检查结果有哪些？
4. 正常处理是什么？
5. 其他分支是什么？
6. 是否存在第二次判断？
7. 适合制作成哪一种说明图？

### 练习 3：制作第一张草图

根据练习 2 的内容，先用纸笔或文本画出处理流程。

要求：

- 必须有明确标题。
- 必须有开始位置。
- 必须展示检查条件。
- 必须展示不同处理结果。
- 必须展示审批通过和未通过的结果。
- 不允许自行增加原文中没有的业务规则。

本练习暂时不要求使用专业绘图工具。

## 13. 本章总结

制作说明图时，最重要的不是先选择工具，也不是先考虑颜色和布局。

正确的顺序是：

1. 明确制作目的。
2. 明确阅读对象。
3. 理解原始资料。
4. 整理业务信息。
5. 确定说明图类型。
6. 设计逻辑结构。
7. 编写准确的日语。
8. 使用工具绘制。
9. 从客户角度检查。

请记住：

**好的说明图，不是让制作人员觉得漂亮，而是让阅读者不需要反复询问，也能够正确理解内容。**
